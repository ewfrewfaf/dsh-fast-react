# 快速反应 · 效率验证测试方案（2026-11-07）

> 原则：**每一项都要有对照组，没有对照的改动不进主干。**
> 所有指标从 `events.jsonl` + `detail.jsonl` 量化，不靠主观感觉。

---

## 0. 开测前置（每次开机都跑）

```bash
node tools/preflight.mjs <端口>     # 26 项检查，必须有 0 失败
node tools/stats.mjs "" <窗口小时>  # 看机制活动基线
```

前置不通过就不要测——否则数据全废。

---

## 1. 测试分层

| 层 | 目的 | 成本 | 何时跑 |
|---|---|---|---|
| **L1 静态** | 代码/配置/接口契约没坏 | 0 | 每次改完 |
| **L2 单机制 A/B** | 单个开关开/关的差异 | 模型调用 | 本轮重点 |
| **L3 端到端** | 真实任务整体表现 | 模型调用 | L2 通过后 |

本轮只做 **L1 + L2**。L3 等 L2 有了结论再说。

---

## 2. 统一度量口径

| 指标 | 来源 | 为什么用它 |
|---|---|---|
| `墙钟耗时` | `api-task` 到 `deliver` 的时间差 | 用户真正感知的 |
| `工具调用数` | `detail.jsonl` 的 `tool` 事件 | 模型往返的直接代理 |
| `唤醒次数` | `detail.jsonl` 的 `wake` 事件 | 编排开销 |
| `失败/契约错` | `tool.ok=false` / `callErr` | 返工的直接证据 |
| `压缩次数` | `event('ctx-compact')` | 上下文效率 |
| `token` | `metrics.json` 累计 | 成本 |

**每个 A/B 至少 3 次重复**，取中位数。单次差异一律不算结论。

## 3. L2 各项设计

### T1 · todo 镜像（`todoMirror`）

| 项 | 内容 |
|---|---|
| 假设 | 镜像是纯投影，**不应改变任何耗时** |
| 任务 | 一个 5+ 步的编码任务（读→改→验证） |
| 对照 | `todoMirror=true` × 3 / `false` × 3 |
| 看什么 | 墙钟、工具调用数、`token` |
| 期望 | **无显著差异**（若差异 > 10%，说明镜像有隐藏成本，要查） |
| 判定 | 差异 < 10% ⇒ 保留（UI 可见性白赚）；> 10% ⇒ 关掉 |

### T2 · 终局对照审（`finalAudit`）

| 项 | 内容 |
|---|---|
| 假设 | 它会**增加一次后台唤醒**，但降低"交付缺验收" |
| 任务 | 3 个「容易漏验收项」的任务（多条件需求） |
| 对照 | 开 × 3 / 关 × 3 |
| 看什么 | `deliver-audit{ok:false}` 次数、终局到交付的墙钟增量、是否出现补做 |
| 期望 | 能抓到至少 1 次缺项；墙钟增量 < 20s |
| 判定 | 抓到 ≥1 次 ⇒ 保留；一次没抓到 且 增量 > 20s ⇒ 重新评估 |

### T3 · 首帧带原文（`firstFrameEcho`）

| 项 | 内容 |
|---|---|
| 假设 | 把等待变执行，但可能产生返工 |
| 前置 | 需要一个**后台明显慢**的场景（把 backModel 换成更慢的模型，或人为拉长首帧） |
| 对照 | 开 × 3 / 关 × 3 |
| 看什么 | 首帧耗时、前台在等待期做的动作数、返工（`rework-detected`）、最终完成时间 |
| 期望 | 完成时间更短，且返工不增加 |
| 判定 | 时间缩短 ≥15% 且返工不涨 ⇒ 保留；返工上涨 ⇒ 只允许只读动作 |

### T4 · 统一轮询（`pollUnified`）

| 项 | 内容 |
|---|---|
| 假设 | 前端 CPU/IO 优化，**不影响任务耗时** |
| 成本 | 零模型调用 |
| 测法 | 打开面板放 5 分钟，用浏览器 Performance 或简单计时器统计 `/fr/api/status` 请求数 |
| 对照 | `pollUnified=true`（1 个心跳）vs `false`（4 个独立 interval） |
| 期望 | 开时请求数明显更低，且页面不卡 |
| 判定 | 请求数降低 ⇒ 保留 |

### T5 · 结果剪枝（profile 层 `tool-result-pruner`）

| 项 | 内容 |
|---|---|
| 假设 | 减少上下文膨胀 → 减少压缩次数 |
| 任务 | 长任务（≥10 步，中间有大量 grep/read） |
| 对照 | 插件 `disabled:true` × 3 / `false` × 3（**需重启**） |
| 看什么 | `ctx-compact` 次数、`token` 总量、是否有"结果被截断导致重读" |
| 期望 | 压缩次数下降，token 下降 |
| 风险 | 剪枝把有用信息砍掉 ⇒ 前台重新读同一文件（`read` 次数上涨） |
| 判定 | 压缩↓ 且 `read` 次数不涨 ⇒ 保留；`read` 明显上涨 ⇒ 放宽阈值或关掉 |

### T6 · 性能档位（`tier`）

| 项 | 内容 |
|---|---|
| 假设 | `speed` 更快但质量降，`max` 反之 |
| 任务 | 同一批 3 个任务 × 三档 |
| 看什么 | 墙钟、token、完成度（是否跑完所有步骤）
| 判定 | 先看 `speed` 是否真的更快（若 glm 不支持 effort，**三档可能完全一样**——这正是要验证的） |

### T7 · 扇形 worker（`fanoutWorkers` / `workerMax`）

| 项 | 内容 |
|---|---|
| 假设 | 并行检索更快 |
| 任务 | 一个需要扫多处的检索任务（如"找出所有引用了 X 的文件并总结"） |
| 对照 | A：`retrieval` + `fanoutWorkers=true`（派 2 worker）<br>B：`retrieval` + `fanoutWorkers=false`（前台自己并行） |
| 看什么 | 墙钟、token（worker 是完整会话，token 会高）、完整度 |
| 判定 | 墙钟明显低且 token 涨幅可接受 ⇒ 保留；否则退回 |

### T8 · 后台审 diff（`reviewDiffEnabled`）

| 项 | 内容 |
|---|---|
| 假设 | 少返工，但多一次唤醒 |
| 任务 | 3 个多文件改动任务 |
| 对照 | 开 × 3 / 关 × 3 |
| 看什么 | `review-diff` 触发次数、返工、墙钟 |
| 判定 | 触发过且返工下降 ⇒ 保留；从未触发 ⇒ 阈值太严，调低或删掉 |

---

## 4. 顺序（先便宜后贵）

| 顺序 | 项 | 理由 |
|---|---|---|
| 1 | **T4 轮询** | 零模型成本，先排掉 |
| 2 | **T6 档位** | 先验证 glm 上 effort 是否真的无效（决定后面怎么测） |
| 3 | **T1 todo 镜像** | 假设是"零影响"，最容易验证 |
| 4 | **T5 剪枝** | 影响所有会话，要先确认没副作用 |
| 5 | **T2 终局审** | 需要"容易漏验收"的任务，要挑 |
| 6 | **T8 审 diff** | 依赖 coding 模式真的触发 |
| 7 | **T7 扇形** | token 成本最高 |
| 8 | **T3 首帧** | 需要人为制造慢后台，最后做 |

## 6. 中止条件

出现以下任一情况立即停止并回滚：

- 插件 `/fr` 打不开或返回空响应
- 前后台接线失效（`wiring.state != wired`）
- `detail.jsonl` 不再增长
- 出现 0.2.2 的 `agent/request proposed ... after step preparation fixed` 报错（说明有插件还在改路由）
