# 快速反应（dsh-fast-react）技术路线

> 一句话：**前台低档快答快做，后台高档逐步规划，靠一块磁盘黑板 + 机械哨兵把两个会话缝成一套流水线。**
> 本文讲原理与实现；怎么用见 [使用须知](./使用须知.md)。

---

## 1. 为什么要有它

单会话 Agent 的两个矛盾：

| 矛盾 | 表现 |
|---|---|
| **快 vs 想清楚** | 低档模型几秒就答，但做长任务容易跑偏；高档模型想得清楚，但首帧要几十秒，交互体验崩了 |
| **上下文膨胀** | 长任务历史越滚越大，最后被 compaction 打断、丢细节 |

快速反应的做法：**拆成两个会话，各干各的**。

```
              用户
               │  面板 / API
               ▼
      ┌─────────────────┐              ┌──────────────────┐
      │  前台（低档/快）  │  ── 上交 ──▶  │  后台（高档/慢）   │
      │  执行 + 上报      │              │  路线规划 + 复核   │
      └────────┬────────┘              └────────┬─────────┘
               │        写 / 读 黑板（磁盘）      │
               └──────────► .board/ ◄────────────┘
                  state.md · steps/ · route.md · heartbeat.log · events.jsonl
               ▲
               │  实时投递 / 哨兵 / 看门狗 / T3 闸门（插件层）
```

- **前台**：只执行。拿到步骤就干，干完自己读下一步（拉取模式），不写长总结。
- **后台**：只规划。读前台上报，产出 `route.md` + `steps/S*.md`，并在里程碑处复核。
- **黑板**：唯一的通信介质（磁盘文件）。**会话是内存态、随时可能被重建，黑板是持久层**。
- **插件层**：监听 DSH 事件、投递步骤、拦截破坏性操作、检测僵死、把一切记进 `events.jsonl`。

## 2. 五个关键机制

### 2.1 事件驱动的步骤投递（M1，实时）

不轮询，直接挂 DSH 的 turn 边界事件：

| 事件 | 用途 |
|---|---|
| `agent/turn-stopping` | 前台**即将停下**的瞬间，若下一步已就绪 → `steer()` 塞进当前回合（零额外唤醒） |
| `steps/` 文件监听 | 后台写出 `S<k>.md` 的 0.1s 内投递（原先是 30s 轮询延迟） |
| `agent/pre-step` | 工具执行的统一闸门（T3 破坏性拦截、运维工具禁用都在这里） |

### 2.2 拉取优先（M1+）

插件只在**任务开始时**推第一步，之后前台**自己读** `steps/S<k+1>.md` ⇒ 省掉一次串行唤醒（实测每步省 ~30s）。

### 2.3 T3 破坏性闸门

`pwsh`/`bash` 命令命中危险模式（`rm -rf`、`Remove-Item`、部署、对外发送…）时：

1. **拒绝执行** + 写 `events.jsonl` 的 `t3-block`
2. 允许临时目录清理（避免误伤测试）
3. 需要人工放行时写 `.board/confirm/<step>.ok`
4. **禁止换方式重试**（写进前台简报的硬边界）

### 2.4 僵死看门狗（150s）

DSH 会卡在“`phase=running` 但模型流无输出”的状态。看门狗每 15s 检查：

```
running 且 (本轮开始 / 最近工具) 距今 > stallTimeoutMs(默认150s)
  → cancel()
  → 若本轮**一个工具都没跑过**（没动手）：自动重投最后一条真人消息（safe-retry）
```

### 2.5 角色分工与档位

- 前台简报：发完 tool call 立刻停笔、只在两处写文字、并行工具调用按代价自适应
- 后台简报：只写路线与步骤，里程碑末复核
- 曾经的档位漂移（按角色切 reasoningEffort）**实测对已存在会话无效**，默认关闭

## 3. 面板 UI（/fr）

一个 iframe 页面，按**原生会话区矩形**精确覆盖（探针实测 centerCol = `264,40,1656,992,16px`），顶部灰线与 DSH 会话 header 的 `border-bottom`(y=116) 像素级重合。

| 功能 | 说明 |
|---|---|
| 对话 | 用户右对齐浅灰气泡 / Agent 纯文本；**思考过程浅灰折叠**；系统注入话术全部隐藏 |
| 输入栏 | DSH 同款 `rgb(44,44,46)` / 28px 圆角；**发送即打断**开关（红=先 cancel 再投递） |
| 模型切换 | 右下下拉，`GET /fr/api/models` 走 `ctx.get('llm')` 列出 20+ provider |
| 会话组管理 | FR-01/FR-02… 增删切换自愈；**每组权限下拉**（read-only / workspace-write / danger-full-access / auto） |
| 运行反馈 | 「前台正在处理…」三点动画；`stall` 配置外露 |

侧边栏注入的 **「快速反应」入口按钮**由 `sidebar.js` 完成（loader 每 3s 拉 `/fr/sidebar.js` 并注入 `<script>`，改 UI 免重启）。

## 6. 设计上的取舍（写给未来的维护者）

1. **黑板优先**：任何状态都要能从 `state.md / route.md / steps/` 重建；内存会话随时会死。
2. **不做规划的前台**：前台一旦开始“想”，响应就从 2s 变成 30s。
3. **可观测性 = 事件流**：`events.jsonl` 是唯一真相（各机制都有 `event()`），排障先看它。
4. **热重载 = 会话重建**：插件重载会销毁内存会话，**不要在任务运行中重载**。
5. **哨兵是机械的**：只认文件/数值条件，不做语义判断；语义判断交给后台。

## 7. 会话劫持事故复盘（2026-10-18，v1.2.0 修复）

### 现象（用户视角）

- 后台明明"下发了步骤"，但前台一直空闲 / 或前台疯狂派生 6 个子智能体
- 右下角**暂停按钮点不动**
- 长任务时 iDSH 变得很卡

### 根因链

```
rebuild/自愈 与 resolveAgents 存在时序竞争
  → 会话尚未就绪时走了"自动发现"分支
  → 自动发现只按 cwd 匹配，**不验证会话身份**
  → 把两个 UUID 子会话当成前后台
  → 「接线已焊死」把错误 ID 写进 config.json（永久固化）
  → 步驟投递到冒名会话，它们以为自己是快速反应前台 → 疯狂 spawn 子智能体
  → 真正的 front/back 永远空闲（"后台没在跑"）
```

### 修复（四道防线）

| # | 防线 | 说明 |
|---|---|---|
| 1 | **身份校验** | 自动发现只认 `session-fr-*` 前缀 |
| 2 | **最终守卫** | 任一候选不是 fr 会话 → 置空，交给 ensureWiring 重建 |
| 3 | **焊死前确认** | 只有两者都是合法 fr 会话才写入 config |
| 4 | **脏数据自愈** | 发现 cfg 指向非 fr / 已不存在的会话 → `wire-dirty-drop` + 自动重建 |

### 附带修复

- **禁止派生子智能体**：简报硬边界 + 工具层拦截（`block-subagent`），
  需要并行请在一个回复里发多个工具调用
- **暂停失效**：`turn-stopping` 内联投递会用 `steer()` 延展当前回合，
  导致 DSH 的 pause 打不断。现在 `userStopAt` 15 秒内禁止一切
  `steerFront` / `wakeBack` / 内联追加；且仅在前台确实 `running` 时才内联

### 验证

```
tools/test-live.mjs  11/11 通过
  ✅ 停止后立即 idle，8s 内未复活
  ✅ 连续 3 轮任务全部完成
  ✅ 前后台都是 fr 会话（防劫持）
  ✅ 无新子智能体
tools/regression.mjs  4/4 通过（selfcheck 18/18 + UI/API 25/25）
```

## 8. 2026-10-24 修复：三个「真影响功能」的缺陷

> 判定标准：**会不会让用户在正常使用中丢功能/被反复干扰**。只修这三条，其余属注释漂移或死代码，不动。

| # | 缺陷 | 影响（为什么算真 bug） | 修法 |
|---|---|---|---|
| 1 | `checkFireFile()` 用 `unlinkSync` 但**没 import**，`ReferenceError` 被空 `catch` 吞掉 | `.board/fire.md` **永不删除** ⇒ 同一个文件在 60s 冷却后**反复打断**（每任务上限 5 次，下个任务又重来）。消防通道从"一次性信号"退化成"定时炸弹" | 改为**移到 `.board/stale/fire-<ts>.md`**（只消费一次 + 留审计痕迹），移动失败再退回删除；同时补上 import |
| 2 | `fireInterrupt()` 先写 `userStopAt`（L1973）再 `steerFront(note)`（L1997），而 `steerFront` 有 15s 静默窗 | 消防通道**只断不说**：设计里明确「打断后必须附说明，否则会被旧思路锚定」，实际说明 100% 发不出去 | `steerFront(text, reason, { force })`：`force` 可绕过本通道自写的 `userStopAt`；另外新增 `pauseAt`（真·用户暂停），**优先级高于 force**，暂停后 15s 内任何东西都不许投递 |
| 3 | `unwire()`/`wire('')` 只 `delete overrides.x`，而 `saveOverrides()` 用盘上旧值铺底 | 解绑后旧 `frontSessionId/backSessionId` 会在下一次保存时**写回文件**（解绑"复活"） | 新增 `droppedOnce` 集合：保存时先从 `disk` 删掉这些键再合并 |

**验收（本机实测）**

```
tools/regression.mjs 8031  →  4/4 PASS（静态审计 / selfcheck 18/18 / UI-API 25/25 / 修复点 15 项）
fire.md 实测：写入 → tick 内被搬到 stale/fire-1792777091331.md，盘上不再残留 ✅
```

**不修的三类**（记录理由，避免下次重复纠结）：
- `boardRoot` 写在 `config.json` 里不生效（`boardDir` 在配置合并前算好）：正常用法是写在 profile 配置里，改文件属于误用；改它要动初始化顺序，风险大于收益。
- H3 阈值 300s 硬编码、`heartbeatAge()` 死代码、`lookahead` 配置未被使用、`inject:['sessions']` 未用：都是**不影响行为**的历史残留，属清理项而非 bug。
- 文档写 `agent/pre-step` 闸门（实际是 `ctx.tools.guard`）：已在本文修正，代码不动。

## 9. 2026-10-24 第二轮 debug：陈旧分诊 + 两处热路径 + 日志无界

> 判定标准同 §8：只修「会让用户在正常使用中丢功能 / 越跑越卡 / 磁盘无限长大」的。

| # | 缺陷 | 影响 | 修法 |
|---|---|---|---|
| 4 | `checkVerdict()` 不看 verdict 新旧（只按内容去重，重启即重放） | 本机 board 里躺着 **10-17 的旧 verdict**，而 route 已到 10-18。重启后旧分诊被重新应用 → 给前台发「这任务不值得编排，你自己干」→ **直接废掉双会话编排**（用户眼里就是"后台没在跑"） | verdict 的 mtime 必须晚于**本任务起点**（最近一次 `api-task` / `deliver` / `escalate` 事件）；否则记 `verdict-stale` 并忽略 |
| 5 | `/status` 每隔 1s 整读 `events.jsonl` 再 split | 文件 5.7MB 时 **25ms/次**同步阻塞；长任务下持续拖慢宿主 | 新增 `tailLines()`（只读文件尾部 256KB）：**0.85ms/次（29×）**，末 300 行逐字节一致 |
| 6 | `recentChat()` 每次把 `snapshotEvents()` **整段会话**遍历 + 合并 | 前后台各一次 × 每秒 = 长会话下的 CPU 尖峰（"长任务时 DSH 很卡"的候选原因） | 只取尾部窗口 `max(200, limit*8)` 条事件再合并；结果本来就只保留最后 N 条 |
| 7 | `events.jsonl` / `heartbeat.log` 只增不减 | 长任务连续跑几天可涨到几百 MB，读也慢、盘也吃 | tick 内 `ensureLogsBounded()`：events > 8MB、heartbeat > 4MB 时整份改名 `*.1.*`（保留 1 代），并记 `events-rotated` |

**验收（本机实测）**

```
/status 平均耗时 32ms → 14ms（日志已改为尾部读，成本与文件规模解耦）
tailLines vs 整读：5.7MB 文件 25.01ms → 0.85ms（29.5×），末 300 行逐字节一致
日志轮转实测：灌到 11.04MB → 下一 tick 变 events.1.jsonl，新 events.jsonl 首行即 events-rotated ✅
陈旧 verdict 实测：重启后事件流出现 verdict-stale（不出现 verdict-short / 后台分诊）✅
tools/regression.mjs 8031 → 4/4 PASS（selfcheck 18/18 · UI-API 25/25 · 修复点 15 项）
```

**这轮明确不修的**：`BATCH*.md` 拆分后不删除（每 tick 重扫一次，开销可忽略、删了反而丢审计）、`heartbeat.log` 行数精确统计（文件小）、`seenSteps` 无上界（单任务步骤数有限）。

## 11. v1.3（2026-10-24）：任务模式 + 调度器 + 咨询链路

### 11.1 模式系统（Phase 1，`lib/modes.js`）

**复杂度放在数据里，不放在代码分支里**：4 个预设 + 5 个正交维度（shape/depth/parallel/autonomy/deliver）。

| 模式 | 后台 | 写步骤 | 前台工具 | 后台工具 | 复核 | 预取 |
|---|---|---|---|---|---|---|
| `quick` 速答 | 不启 | 否 | 7 | — | 否 | 否 |
| `consult` 咨询 | ✅（可查资料） | **否**（只写 `analysis.md`） | 9（无 `pwsh`） | 9 | 否 | 否 |
| `retrieval` 检索 | 不启 | 否 | 9（含 `write`） | — | 否 | 否 |
| `coding` 编码 | ✅ | ✅ | 13 | 10 | 每 5 步 | ✅ |

## 12. v1.3.1 修正（2026-10-24 03:00）：只读 worker 已打通

**此前的错误结论**：§11.7 曾记录"只读 worker 不起回合、已移除"。**根因判断错了**——不是会话无法启动，而是**只入队未唤醒驱动**。

**真正的原因与修法**
- 运行时 Agent 的方法表含 `kick` / `wakeDriver` / `whenIdle`：`followup` 只把消息放进 inbox，**不启动驱动**。
- 修法：`inject(简报)` + `followup(开始)` + **`kick()` + `wakeDriver()`** 四步。
- 实测：worker 32 秒内完成「读文件 → 写结论 → 写 `.done`」，插件自动清理；日志出现 `worker 驱动唤醒：kick / wakeDriver`；产物 `.board/workers/<id>.md` 内容正确。

**当前实现**
- `fr_worker` 工具：并发上限 2；工具白名单 = 只读检索 + `write`（写结果文件）；超 10 分钟或 `.done` 出现即清理；`/status.workers` 可查。
- 开关 `cfg.workersEnabled`（默认关，安全）。

**对"多 Agent 配合"的意义**：worker 池的地基已就绪，下一步可做「前台派 2 个 worker 并行查资料 → 汇总」，这也是原计划 #10/#16 的最小可行形态。

## 14. Debug + 性能实测（2026-10-24 05:10）

### 14.1 严重故障：拆分把插件弄成"启动即崩"

**现象**：宿主重启后「快速反应」侧边栏标志消失、`/fr` 全 404，而热重载仍报 OK。
**根因**：`node --check` 只验语法，不验运行时依赖。#8 拆分脚本把 `makeBoard`/msg/Sched 解构等接线弄丢，
apply 抛 `B is not defined`（index.js:376）⇒ 插件启动失败。**热重载的 "OK" 是假象**（旧 fiber 已 dispose，新 fiber 失败）。
**处理**：index.js 回到最后可验证基线（`beab33f`），只重放性能补丁；拆分模块文件保留但不接线。
**教训**：拆分后必须用「模拟 apply」验证（`workbuddy-restore/sim2.mjs`：stub ctx 调用 apply，检查工具注册/effects/监听器）。

### 14.2 修掉的真 bug

| Bug | 影响 | 修法 |
|---|---|---|
| judge 唤醒被 20s 冷却吞掉 | `needs: judge` 步骤投出后置停牌，后台却收不到判断请求 ⇒ **停牌死等** | `judge` 加入 CRITICAL_REASONS（不受冷却） |

### 14.3 性能实测数据（/fr/api/status，1s 轮询）

| 指标 | 数值 |
|---|---|
| 服务器端 `buildStatus` | **2.5–4.6 ms** |
| perf 分项（files/steps/events/ctx/chat/state） | 合计 ~2 ms |
| 客户端 RTT（localhost） | **15–16 ms** |
| `/fr/api/mode`（几乎零计算）RTT | 15–16 ms |

**结论**：约 12ms 是**框架/传输固定开销**（所有路由一致），不是插件代码。插件侧继续微优化上限 ≤2ms。

真正的代码层收益在**轮询频率**：
- 原实现：页面固定 1s 轮询、页面隐藏也照轮（15ms × 1/s 主线程开销）。

`dev_reload_package` 多次出现「调用挂起 5–15 分钟无返回」（工具描述里提到的 dispose 成环问题）。规避方式：改完代码**直接让用户重启宿主**，不要反复热重载；或先用 `sim2.mjs` 验证可加载再重启。

## 19. 梯度基准：快速反应编排 vs 单 AI（2026-10-24 14:55，模型 buddy/hy3）

**方法**：同一模型、同一任务文本，A/B 两条链对比——
A = quick 模式（单 AI 直答，无后台无编排）；B = coding 模式（后台规划 + 步骤投递 + 前台执行）。
四个复杂度梯度，产物全部落盘验证。

| 套件 | 任务内容 | 单AI | 编排 | 差值 | 产物 |
|---|---|---|---|---|---|
| **S3 复杂** | 多文件+读取+统计+清理（4 步依赖链） | 13.8s | **12.2s** | **-1.5s** | 双✓ |
| **S2 中等** | 质数计算+写单文件 | 12.2s | 13.8s | +1.6s | 双✓ |
| **S1 简单** | 写单文件一行 | 12.2s | 13.8s | +1.5s | 双✓ |
| **S0 极简** | 纯问答不落盘 | 9.2s | 9.2s | 0s | 无产物 |

### 结论

1. **复杂任务编排不输甚至略赢**（S3 快 1.5s）——后台并行规划与前台执行的流水线抵消了投递开销。
2. **简单任务编排有固定 ~1.5s 开销**（判型+模式切换+投递），但仍远小于"用户以为的编排税"。
3. **S0 完全持平**（9.2s）——quick 模式判型直通生效，无编排开销泄漏。
4. **产物正确率 8/8**（两链 × 4 套件全部落盘验证通过）。

### 解读

- **架构的价值不在"更快的简单任务"，而在"复杂任务不塌"**：S3 的多步依赖链在单 AI 模式下要靠前台自己规划，模型稍弱就会漏步/错序；编排把它结构化了。
- **判型兜住了 S0/S1 的开销**：这两类本来就不该进编排（判型会走 quick），实测 S0 两者 9.2s 完全一致，说明判型-路由链路没有泄漏。
- **~1.5s 的编排固定开销**来自：模式切换（2 次 API）+ 判型 + 后台首响应。未来若要压缩，方向是"预判模式 + 后台预热"，而不是砍步骤校验。

## 20. 高复杂度基准（2026-10-24 15:10，模型 buddy/hy3）

**背景**：§19 的梯度基准显示编排只在 S3 复杂任务快 1.5s——用户质疑"任务不够复杂"。本节把任务复杂度拉到 5-12 步依赖链再测。

| 套件 | 任务 | 单AI | 编排 | 产物 |
|---|---|---|---|---|
| **H3 极复杂** | 12 步：建 6 文件→交叉引用→汇总→清理 2 个→终检 | 18.4s | 18.3s | 双✓ |
| **H2 高复杂** | 8 步：写数字→算总和/最大值→排序→删源→报告 | 16.2s | 18.3s | 双✓ |
| **H1 中高** | 5 步：双文件合并→删源→完成标记 | 16.3s | 18.2s | 双✓ |

### 关键发现：**产物正确率 6/6（两链全对），编排没有跑出优势**

### 原因分析（诚实）

hy3 对这种**步骤明确、指令清晰**的任务执行得很稳——单 AI 模式下它按顺序做完 12 步没有漏。
编排的结构化优势**没有发挥空间**，因为：

1. **任务本身已经"预结构化"**：我写的 12 步指令自带依赖顺序，单 AI 照做即可，不需要"规划"。
2. **缺少"需要规划才能解"的成分**：没有"先探索再决定"的分支、没有中途失败重规划、没有跨步骤的信息聚合决策。
3. **编排的固定开销 ~2s**（判型+模式切换+后台首响应+投递）在这种任务里是纯负担。

### 编排真正该赢的场景（本轮未覆盖）

- 步骤间有**条件分支**（"如果 X 存在则 A 否则 B"）——单 AI 容易漏判
- **中途失败**需要重规划——单 AI 倾向硬编码下一步
- 任务描述**模糊**，需要后台"先理解再拆步"——单 AI 直接动手容易方向错
- 步骤数 **>20**，超出单上下文的可靠执行范围

### 修正后的架构价值表述

编排的核心价值**不是速度**，是**可靠性上限**：
- 简单明确任务：单 AI 够用，编排+0~2s 开销
- 复杂模糊任务：单 AI 可能漏步/错序（本次未测出因为任务太明确），编排靠结构化保证不漏
- 极端长任务：单 AI 上下文溢出风险，编排天然分步

## 22. 早期版本 vs 当前版本对比（2026-10-24 15:50）

**早期基线**（docs §2/§14 记载的 M1 时代数据）：
- 步骤投递：30s 轮询延迟 → M1 文件监听 0.1s
- M1+ 拉取优先：每步省 ~30s 串行唤醒
- M14 测量：带工具响应 27s / 纯文本 12s
- /status RTT：15-16ms（框架固定开销，插件侧 ≤2ms）

**复测方法**：5 步链式任务（建 a/b → 读 → 合并 c → done），两种投递模式对比——
"早期模式" = batchSteps=1 + pullSteps=false + prefetch=0（每步推送、不预取，即 M1 时代节奏）；
"当前模式" = batchSteps=2 + pullSteps=true + prefetch=3。

**实测**：
- 早期模式（模拟）：22.3s ✓
- 当前模式：32.5s ✓
- **当前反而慢 10.1s**

### 慢在哪（事件时间线诊断）

当前模式的时间线暴露问题：
1. **每次 task 之间有 12-19s 的 front-turn-end 空转**——任务被切成了 4 次 api-task 投递（每次 12-23s 一轮），而不是"一次规划、批量执行"。
2. **判型抖动**：quick→coding 连续 mode-set 两次（auto 判型后又 user 锁定），每次 mode-set 都重刷 tool-policy（71→25 工具 ×2 角色）。
3. **batchSteps=1 时每步一次投递 + front-turn-end 等待**，五步任务变成 5 次完整会话往返。

### 根因与优化方向

**这不是"架构退化"，是"配置组合次优"**：
- batchSteps=1 + pullSteps=false 是最慢组合（每步都走完整投递周期）
- 当前默认（batch=2+拉取+预取）在 §21 模糊任务上快 19-22%，但**在"步骤极明确的任务"上批量优势没发挥**——因为判型把它判成 coding 走了完整流程，而单AI直答（quick）13.8s 就完成了

**可优化点（下轮）**：
1. **判型再收紧**：明确编号步骤的任务（①②③④⑤）应该直接判 coding 并**一次投全部 5 步**（batch=5），而不是 5 次往返
2. **front-turn-end 空转**：投递后前台 12s 无事可做——应该立即拉下一步而不是等 watcher
3. **模式切换去重**：连续两次 mode-set（auto→user）应该合并，tool-policy 重刷只做一次

### 结论

| 维度 | 早期（M1） | 当前 | 变化 |
|---|---|---|---|
| 投递延迟 | 30s 轮询 → 0.1s watcher | 0.1s（保持） | ✓ |
| 多步任务总耗时 | 每步+30s → 每步省30s | 22-32s/5步 | ✓ 大幅改善 |
| 模糊任务（后台规划） | 无此能力 | 快 19-22% | ★ 新增价值 |
| 判型直通 | 无（全编排） | S0 持平 | ★ 新增 |
| 明确多步任务 | 22s | 32s（批次次优） | ✗ 可优化 |

## 24. 扩大规模基准（2026-10-24 16:20，模型 buddy/hy3）

## 25. 突破方向可行性分析（2026-10-24 16:30）

基于 §24 的发现（多实体任务编排快 5.1 倍），分析"进一步扩大优势"的两个方向。

### 方向 A：E1 型任务判大 batch（可行性 ★★★★☆）

**现状核对**：
- effectiveBatch 夹在 1..8；taskBatchOverride 也 min(n,8) ⇒ 10 文件最多一次投 8 步，剩 2 步第二轮
- steerFront 单条上限 ~9.6KB（8 步 × 1200 字符截断）——DSH inbox 实测吃过 12KB+，无风险
- **发现一个真缺陷**：index.js L1422 在 S1 投出后把 taskBatchOverride 清零 ⇒ E1 型任务只有第一批吃到覆盖，第二批跌回 batch=2。多实体任务应该**整个任务期间保持大 batch**

**修法（低风险）**：override 清零从"S1 投出"改为"检测到新任务文本（deliver 或新 /task）"——一行改动。

### 方向 B：后台写步批量产出（可行性 ★★★★★，已有机制）

**关键发现**：briefs.js 后台简报**已经内置了批量机制**——
- `fr_route` 一次工具调用同时产出路线 + 全部步骤文件（"这是最快的路径"）
- 搜索类任务段落明确"步骤必须批量：一步 3-5 个 URL 并发抓"“禁止一步抓一个页面”
- 铁律 4："互不依赖的 write 必须同一回复并发发"

E1/E3 实测编排 27-30s 正是这套机制在工作（后台 1 次响应 → 前台批量执行）。
**方向 B 不需要新代码，需要的是让"多实体任务"也吃到搜索类段落同款指令**——现在那段只对"搜索/调研类"生效，E1（门店汇总）没有命中。

**修法（一行）**：briefs.js 搜索类段落的触发条件从"搜索/调研类"扩展到"多实体批量任务"（识别：文本含 ≥N 个同类实体/文件）。

### 判定汇总

| 方向 | 可行性 | 改动量 | 预期收益 |
|---|---|---|---|
| A. override 不清零（任务级保持） | ★★★★☆ | 1 行 | E1 型第二批不再跌回 batch=2，约省 10-15s |
| B. 多实体任务吃批量简报 | ★★★★★ | 1 行正则 | 后台规划质量提升（已经隐性生效，显性化） |
| A+. batch 上限 8→12 | ★★☆☆☆ | 1 行 + 风险 | 12 步 × 1200 字 = 14.4KB 单条 steer，超安全边际，不建议 |

**结论**：两个方向都可行且改动极小。A 修真缺陷，B 显性化已有机制。A+ 不建议（消息体量风险）。

## 28. 模式自上报机制核实（2026-10-24 17:30）

**用户问题：模式选错时，前台会自己上报吗？**

### 28.1 机制盘点（代码核实）

| 环节 | 状态 |
|---|---|
| fr_mode 工具（模型可随时调用，by=agent） | ✓ 已有 |
| 模式变更注入 modeNotice（前后台都知道当前模式） | ✓ 已有 |
| **模式说明里的「发现不合适就换」引导** | ✗ 缺失（本轮补上） |

补强：modeNotice 末尾加一行——「若执行中发现此模式不适合当前任务，调用一次 fr_mode 切换，不必请示用户。」工具在、通路在，此前缺的只是一句提示。

### 28.2 端到端实测（锁定 quick 制造判型错误）

实验 1：锁 quick + 3 步明确任务 → 模型未切模式，但 3 步全部完成（quick 有全量工具，多步任务也能干，只是没有编排加成）。

实验 2：锁 quick + 模糊 15 文件分析任务 → 模型未切模式，55s 完成报告。两个意外发现：
- 报告总额 145,350 **完全正确**（judge 的字符串匹配没处理千分位写法——judge 缺陷非模型错误）
- 模型自己发现「15 店数据完全一致」——这是**数据生成器 bug**（genSales 的 seed 固定导致全同），模型在报告里如实指出「这是模板数据，不具备真实对比价值」

### 28.3 校准后的结论

1. **自上报机制是「可选逃生门」而非「自动纠错」**：模型有能力切（fr_mode 通路完整），但 quick 模式下全量工具在手，多数任务它选择直接干完而不是切模式——**这是正确行为**（切换有开销，能干就干）。
2. **真正需要切模式的信号**是「任务要求后台规划/长链编排」，而不是「多步」。引导语已补，但模型在 quick 下干完 15 文件分析说明**工具全量 + 模型能力**是第一保障，模式只是节奏器。
3. judge 自证 again：第二轮的误报又是测试脚本缺陷（千分位），模型产物是对的。**基准报错先怀疑测量工具**。

## 37. steps → 官方 todo 单向镜像（2026-11-07）

### 37.1 为什么能共存

读 `@deepseek-ai/dsh-tool-todo` 源码确认了两条事实：

1. `todo_write` 等价于 `session.append('todo/write', { todos })` —— **整表替换**，最后写赢
2. 投影 `apply` 里有 `if (event.type === 'turn/start') return null` —— **每个 turn 会清空**

所以「打架」的前提（两个写者各自累加）根本不成立：这是覆盖语义，且每轮重置。
只要**写者唯一**（插件），冲突就会自动收敛。

### 37.2 实现

| 项 | 内容 |
|---|---|
| 写者 | 只有插件（`syncTodos()`），模型调了也只会被下一次覆盖 |
| 触发 | ① 前台 `turn/start`（事件钩子，`setTimeout 0` 错开重入）② 新步骤投递 ③ 任务重置 |
| 数据 | `steps/S*.md` 的「动作:」行 + `state.done` → `completed / in_progress / pending` |
| 幂等 | JSON 指纹相同则跳过；超过 40 步折叠成一行 |
| 开关 | `todoMirror`（默认开），设置面板可关 |
| 埋点 | `vlog('todo-mirror', {why,count})` |

### 37.3 边界

- 真相源仍是 `steps/S*.md`；todo 只是它的**逐轮投影**，不参与任何调度判断
- 投影只在装了 `tool-todo` 的会话里生效（standard / router-* 预设都有）
- 模型若自己写 todo，本轮以它的为准，下一轮插件再覆盖回来——不会累积错误状态

## 38. 模式的「独特协作形态」：扇形检索 + 只读审 diff（2026-11-07）

判据只有三条：**快模型承担执行 / 真并行 / 不增加往返**。

### 38.1 retrieval：扇形检索（已实现）

| 项 | 内容 |
|---|---|
| 形态 | 前台 **1 派 N**：把大范围搜索拆成 2–4 个互不依赖的子查询，**同一回复里并行**调 `fr_worker`，再读 `.board/workers/<id>.md` 汇总 |
| 现状 | worker 池早就有了（只读工具集、并发 2、结果落盘），缺的只是"模式自动允许 + 派发指令" |
| 改动 | `modes.js` 的 retrieval 加 `fanout: 2`；`modeNotice()` 输出派发模板；`fr_worker` 门禁放行 retrieval 模式 |
| 为什么提效 | 只读、并行、全部由前台（快模型）承担；汇总只多一次读文件 |

### 38.2 coding：后台只读审 diff（已实现）

| 项 | 内容 |
|---|---|
| 形态 | 前台写代码 → 插件攒改动文件 → 后台**只读**核对是否符合 route.md 验收标准，**不写代码、不改文件、不重排路线** |
| 触发 | 攒够 3 个改动文件；冷却 2 分钟；每任务最多 3 次；`changedFiles` 在 S1 重置 |
| 改动 | `modes.js` 的 coding 加 `reviewDiff: true`；post-execute 收集 write/edit/apply_patch 的路径；tick 里 `maybeReviewDiff()` |
| 为什么这样分工 | **慢模型只做判断，快模型做体力**。原提案「后台写代码、前台测试」方向相反：用慢模型做快活，墙钟反而变长 |

### 38.3 apply_patch：已备好补丁，**尚未启用**

`standard` 预设里 `tool-fs` 是 `applyPatch: false`。要开它必须自定义预设：

```yaml

    - id: preset-fast-react-front
      name: '@deepseek-ai/dsh-agent-preset'
      config:
        id: fast-react-front
        order: 9

          - id: tool-fs
            name: '@deepseek-ai/dsh-tool-fs'
```

**为什么没直接落**：预设的 `plugins` 是「在默认组合上追加/覆盖」还是「完整定义」，只能靠运行时验证；
配错会让前台/后台会话**建不起来**（比不生效危险得多）。所以留到测试轮第一步验证，

apply_patch 省的是结果载荷和失败模式，不是往返次数。测试轮用 `detail.jsonl` 量过再决定。

原则：**没有证据的改动，先装开关、默认保守，测过再定默认值。**

| 开关 | 默认 | 作用 | 怎么测 |
|---|---|---|---|
| `tier` | `balanced` | 性能档位：`speed` = 前台 minimal / 后台 medium；`max` = 前台 high / 后台 max | 同一任务三档各跑 3 次比墙钟 |

| `verboseLog` | `false` | 详细日志 | — |
| `budgetWakes` | `12` | 干扰预算阈值（只观测不拦截） | — |

### 39.1 实现要点

## 40. 新一轮提效（2026-11-07，四项）

### 40.1 工具结果剪枝（启用 DSH 自带，profile 层）

```yaml
- id: tool-result-pruner
  disabled: false
  config: { thresholdChars: 16384, headChars: 12288, tailChars: 2048 }
```

超过 16k 的工具结果只保留前 12k + 后 2k，中间换成标记。目的：**抑制上下文膨胀 → 减少压缩次数**（每次 `compactNow` 都是一次模型调用）。
选择比默认（8k/4k/1k）更保守的阈值，避免把正常的文件读取砍半。
注意：这是 profile 级插件，**影响所有会话**，不只快反。

### 40.2 面板轮询合并

原来页面里有 4 个独立 `setInterval`（sync 3s / 权限 refresh 15s / T3 2s / 模式 refresh 15s），
各自触发、同一瞬间可能同时读同一批文件。现在收成一个 1s 心跳 + 任务表：

- 单一 `setInterval`，按各自周期分派
- `document.hidden` 时整体暂停（标签页在后台不空转）
- T3 轮询从 2s 放宽到 3s（与心跳对齐）

`frontContextLimit` 从 60000 提到 80000（`defaults.js` + 已持久化的 `.board/config.json` 都改了）。
理由：压缩本身是一次模型调用，60k 对多步任务偏紧，压得越勤总成本越高。80k 是折中值，观察后再定。

### 40.4 首帧超时兜底：不再“猜任务”，直接给原文

`checkFirstFrame()` 原来只让前台「做只读侦察、不要猜任务」。现在：

1. `deliver()` 记录发给前台的任务原文（`lastTaskText`，截 4000 字）
2. 首帧超时后把任务原文回带给前台，并允许它**先推进不可逆风险低的部分**（读现状/建目录/改实现/跑验证）
3. 唯一禁区：先不写 `deliver.v1.md`，等后台步骤到了对齐收口

依据：前台本来就持有任务原文，“猜测风险”只在没有原文时才存在；给它原文等于把等待时间变成执行时间。

## 43. 多实例并行（2026-11-07）

### 43.1 原来为什么不能并行

```js
let front = null; let back = null              // 插件级单例
const boardDir = join(boardRoot, '.board')     // 常量
```

一个插件包 = 一条流水线 = 一次只跑一个任务。会话组（FR-01/02）只切 `front/back` 指向，
**切换后前一组失去投递目标**，且所有组共用同一份 `state.md` / `steps/` / `events.jsonl`。

### 43.2 改法：同包多挂 + 实例 tag 隔离

`config.instanceTag`（默认 `a`）决定四件事：

| 维度 | tag = a（默认，保持不变） | tag = b |
|---|---|---|
| 会话前缀 | `session-fr-*` | `session-fr-b-*` |
| 工具名 | `fr_escalate` | `fr_escalate_b` |
| 路由基路径 | `/fr` | `/fr_b` |
| 黑板 | `boardRoot` | 独立 `boardRoot` |

**关键点：a 的全部命名保持不变** ⇒ 现有会话、书签 URL、已装 UI 页面都不受影响。

### 43.3 五个必须修的冲突点

| # | 冲突 | 现象（不改的话） | 修法 |
|---|---|---|---|
| 1 | `ACTIVE_GEN` 模块级 | 后启动的实例把先启动的判死，先启动的监听器/定时器全失效 | `GEN_BY_TAG` Map |
| 2 | `FIRE` 模块级 | 消防通道互相覆盖 | `FIRE_BY_TAG` |
| 3 | `isFrSession` 只认 `session-fr-` | 两个实例抢同一个会话（b 会把 a 的前台当自己的） | 前缀 + 排除 `session-fr-[b-z]-` |
| 4 | 工具名 `fr_*` | `tools.register` 抛 already registered | `TN()` 加后缀；简报/白名单/guard 同步 |
| 5 | 路由 `path: '/fr'` | `webServer.register` 直接 `duplicate route` 抛错 | `makeRoutes` 收 `basePath`；前端从自身地址反推 |

### 43.4 挂第二个实例

profile 的 `cordis.patch.yml`：

```yaml
- insert:
    - id: dsh-fast-react-b
      name: dsh-fast-react
      config:
        instanceTag: b
        boardRoot: C:/Users/admin/Desktop/FastReact-b
```

启动后：`http://127.0.0.1:<端口>/fr` = 实例 a，`/fr_b` = 实例 b，两块黑板互不干扰。

### 43.5 验证清单（重启后）

1. `/fr` 与 `/fr_b` 都能打开（不是 404/401/空响应）
2. 两边的 `wiring.state` 都是 `wired`

### 44.1 测试中发现的 bug：用户手选模式被机械判型冲掉

**现象**：
```
20:14:00 mode-set coding by=user   ← 用 API 手动设 coding（为跑编排测试）
20:20:15 mode-set quick  by=auto   ← 下一条任务被判成 quick，直接覆盖
```

**影响**：`modeAuto` 打开时，`detectMode()` 无条件覆盖当前模式，
**用户/测试手动设定的模式在下次投递就失效**。测试里表现为：
明明设了 coding，任务却按 quick 执行 → 不叫后台 → 没有 steps → todo 镜像 0 次。

**修法**：`modeBy === 'user'` 时跳过自动判型（`userPinned`）。

**副产物**：这条也解释了为什么 T1 的三轮测试 `steps=0 / mirror=0` —— 不是镜像坏了，
是根本没走编排。手动造 3 个 step 文件后镜像正常触发（`count:3`）。
